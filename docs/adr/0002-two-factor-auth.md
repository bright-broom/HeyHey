# ADR 0002：2 段階認証（F-04）

- 日付：2026-09-27
- 状態：採用

## 背景

管理者のアカウントは、全会員の申請内容・通報・監査ログに触れられる。
パスワードだけで守っていると、使い回しや漏えい 1 回でコミュニティ全体の情報が外に出る。
要件定義書では F-04 は Should だが、「承認されたメンバー以外には何も見えないこと」を守るうえで、管理者だけは先に必須にする。

## 決定

| 項目 | 採用 | 理由 |
| --- | --- | --- |
| 方式 | TOTP（RFC 6238、SHA1・6 桁・30 秒） | 認証アプリがあれば追加費用ゼロ。メール OTP は Resend 待ちで、メールアカウントの乗っ取りにも弱い。WebAuthn は将来の追加候補 |
| 実装 | `node:crypto` で自前（`src/server/lib/totp.ts`） | 数十行で済み、RFC のテストベクタで検証できる。QR の描画だけ `uqr`（依存ゼロ）を使う |
| 秘密鍵の保存 | AES-256-GCM で暗号化。鍵は環境変数 `MFA_ENCRYPTION_KEY`、会員 ID を AAD に | DB のダンプだけが漏れても突破できない。行の差し替えも検出する |
| 必須の範囲 | 管理者・オーナーは必須、一般会員は任意 | `policy.isAdmin` が `viewer.mfa` を見るので、未設定の管理者は管理権限が働かない（フェイルクローズ）。設定するまで管理画面は設定ページへ誘導 |
| ログインの 2 段階目 | パスワードが通ったら「チャレンジ」（別テーブル・10 分）を発行し、コードでセッションに換える | 半分だけ認証された状態をセッションと別物にし、既存のセッション判定を 1 行も変えずに済ませる |
| 総当たり対策 | チャレンジごとに 5 回、アカウントごとに 15 分で 5 回。ロック中は正しいコードも通さない | パスワードのロックと同じ考え方 |
| リプレイ対策 | 最後に使ったステップを保存し、それ以下は拒否（条件付き UPDATE で原子的に） | 盗み見たコードの使い回しと、同時送信の二重成功を防ぐ |
| 端末をなくしたとき | リカバリーコード 10 個（1 回ずつ・ハッシュで保存）。すべて失ったら運営者が `npm run mfa:reset` | 自己解決の手段と、最後の手段を分ける。運営者の解除も監査ログに残す |
| 有効化・無効化 | 有効化はパスワード＋コード、無効化はパスワード＋コード（管理者は不可） | 乗っ取ったセッションだけで 2 段階認証を仕掛けて本人を締め出す、または外す、を防ぐ |

## 運用上の注意

- `MFA_ENCRYPTION_KEY` を失うと、全員の 2 段階認証が使えなくなる（全員を `mfa:reset` して設定し直す）。パスワード管理アプリなど DB とは別の場所に控える。
- 鍵がない本番（Vercel または `DATABASE_URL` あり）では、開発用の鍵にフォールバックせず設定を拒否する。
- 鍵を替えるときは、暗号文の先頭の版（`v1`）を上げて、旧鍵で復号・新鍵で再暗号化する移行スクリプトを書く（未実装）。

## 未対応（次の候補）

- WebAuthn（パスキー）
- 新しい端末からのログイン時のメール通知（Resend の導入後）
- 管理画面から一般会員の 2 段階認証を解除する機能（現在は運営者のスクリプトのみ）
