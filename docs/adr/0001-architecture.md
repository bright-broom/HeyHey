# ADR 0001：MVP の構成

- 日付：2026-09-26
- 状態：採用

## 背景

許可制 SNS の価値は「承認されたメンバー以外には何も見えないこと」にある。
MVP で最も避けたい失敗は機能不足ではなく、情報漏えい（認可漏れ）である。
あわせて、ローカルですぐ試せることと、そのまま本番の PostgreSQL に移せることを両立したい。

## 決定

| 項目 | 採用 | 理由 |
| --- | --- | --- |
| フレームワーク | Next.js 16（App Router・Server Actions） | 画面とサーバー処理を 1 リポジトリで持てる。認証チェックをサーバー側に寄せやすい |
| DB | PostgreSQL（本番）／PGlite（ローカル・テスト） | 同じ方言・同じマイグレーションで、ローカルは DB サーバー不要。テストはプロセス内で使い捨て DB を作れて速い |
| ORM | Drizzle | SQL に近く、公開範囲の判定を SQL の条件式として 1 か所に書ける |
| 認証 | 自前（scrypt＋DB セッション） | 招待・審査・停止と状態遷移が密に絡むため、外部認証に分けるより 1 か所で管理した方が安全。停止時のセッション即時破棄も簡単 |
| 認可 | サービス層で必ず Viewer を受け取って判定 | Server Actions は公開 HTTP エンドポイント。画面や proxy のチェックに頼らない |
| 公開範囲 | SQL の条件式 `visiblePost` / `visibleComment` を全経路で共有 | 経路ごとの判定のズレを構造的になくす |
| 画像 | sharp で WebP に再エンコード、認証付きルートで配信 | メタデータ除去と、公開範囲チェック付き配信を同時に満たす |
| 監査ログ | DB トリガーで UPDATE / DELETE / TRUNCATE を拒否 | アプリのバグや管理者権限でも改ざんできない |

## 要件定義書からの変更

- **F-14 友達（Should）の最小版を MVP に前倒し**：F-10 公開範囲（Must）の「友達のみ」が友達関係に依存しているため。
- **Supabase（Auth＋RLS）ではなく自前認証＋サービス層の認可**：RLS は強力だが、招待・審査・停止の状態遷移とセットで検証するには、アプリ側に集約してテストする方が確実だと判断した。DB は素の PostgreSQL なので、Supabase の DB だけを使うことはそのまま可能。
- **招待枠「月 3 件」を「直近 30 日で 3 件」と解釈**：月初にリセットされる方式より、まとめ発行の抜け道がない。

## 結果・次の判断が必要な点

- 本番は Vercel（Functions・Neon・Blob private をすべて sin1）に載せた。画像はディスク／Blob を環境変数で切り替える。
- 2 段階認証（F-04）は管理者以上で必須にした。判断の詳細は [ADR 0002](0002-two-factor-auth.md)。
