# 許可制SNS 要件定義書

Sep 26, 2026 · @BrightBroom

## 1. 概要

管理者が承認した人だけが入れる、外部から一切見えないクローズド SNS を作る。Facebook の「フィード・投稿・コメント・リアクション・プロフィール・グループ」を、許可制の前提で最小構成から再設計する。

**目的**

- 信頼できるメンバー同士だけで、安心して近況・情報を共有できる場をつくる
- 公開 SNS で起きる荒らし・なりすまし・情報漏えいを、参加の入口で断つ
- 運営者が「誰が入っていて、誰が何を見られるか」を常に説明できる状態にする

**前提と仮定（未確認のため要確認）**

| 項目 | 本書での仮定 |
| --- | --- |
| 利用形態 | 1 つのコミュニティ（テナント）を 1 運営者が管理する |
| 想定規模 | MVP で会員 1,000 人、同時接続 100 人 |
| 端末 | Web（スマホ対応レスポンシブ）。ネイティブアプリは Phase 2 以降 |
| 言語 | 日本語のみ |
| 収益 | 無料。課金・広告は対象外 |
| 入会方式 | 招待リンク＋管理者承認の二段構え |

## 2. ロールと用語

ロールは 4 つに絞る。権限の細分化は運用が回ってから足す。

| ロール | 役割 | 主な権限 |
| --- | --- | --- |
| オーナー | コミュニティの最終責任者（1〜2 人） | 全権限、管理者の任命・解任、規約の改定、データ出力 |
| 管理者 | 日々の入会審査とモデレーション | 申請の承認・却下、招待枠の付与、投稿の非表示、会員の停止 |
| 会員 | 承認済みの一般ユーザー | 投稿・コメント・リアクション、招待（枠の範囲内）、通報 |
| 申請者 | 登録済みだが未承認 | 自分の申請状況とプロフィール編集のみ。他人の情報は一切見えない |

**用語**

- **招待リンク**：会員・管理者が発行する有効期限付き URL。これがないと申請画面に進めない
- **承認**：管理者が申請者を会員に昇格させる操作。承認までコンテンツは見えない
- **公開範囲**：投稿ごとに選ぶ閲覧範囲（全会員／グループ内／友達のみ）
- **停止**：ログイン不可にするが、データは保持する状態。退会・削除とは区別する

## 3. 参加フロー

入口は「招待リンク → 申請 → 管理者承認」の一本だけにする。招待なしの一般公開登録は作らない。

**入会の流れ**

1. 会員が招待リンクを発行する（有効期限 7 日、使用回数 1 回が既定）
2. 招待された人がリンクからメール認証で登録し、申請フォーム（氏名・所属・招待者との関係・自己紹介）を送る
3. 管理者に通知が届き、招待者名と申請内容を見て承認／却下／保留を選ぶ
4. 承認されると会員になり、初回ログイン時に利用規約へ同意してからフィードに入る
5. 却下の場合は理由テンプレートを添えて本人に通知し、30 日間は再申請不可

**アカウント状態**

| 状態 | 見えるもの | 次の状態 |
| --- | --- | --- |
| 申請中 | 自分の申請内容のみ | 会員／却下 |
| 会員 | 公開範囲内のコンテンツ | 停止／退会 |
| 停止 | ログイン不可 | 会員（復帰）／強制退会 |
| 却下 | ログイン不可 | 再申請（30 日後） |
| 退会 | なし（データは 30 日後に削除） | なし |

**招待の制御**

- 会員 1 人あたりの招待枠を持たせる（既定：月 3 件、管理者が増減可）
- 誰が誰を招待したかの系譜を記録し、問題会員の招待者をたどれるようにする
- 管理者は招待リンクを即時失効できる

**退会・停止**

- 本人退会：投稿を「削除」か「匿名化して残す」かを選べる
- 管理者による停止：理由を必須入力し、監査ログに残す

| --- | --- | --- | --- |

| F-02 | 入る | メール認証による登録と申請フォーム | Must |
| F-03 | 入る | 管理者の審査画面（承認／却下／保留、招待者表示） | Must |
| F-04 | 入る | 2 段階認証（TOTP） | Should |
| F-05 | 見る | ホームフィード（新着順、公開範囲でフィルタ） | Must |
| F-06 | 見る | プロフィール（写真・自己紹介・所属・投稿一覧） | Must |

| F-10 | 書く | 投稿ごとの公開範囲指定 | Must |

## 5. 権限と公開範囲

未ログイン・未承認の人には、URL を直接叩いても何も返さない。これが「許可制」の技術的な中身になる。

| 操作 | オーナー | 管理者 | 会員 | 申請者 | 未ログイン |
| --- | --- | --- | --- | --- | --- |
| フィード・投稿の閲覧 | ○ | ○ | 公開範囲内 | × | × |
| 投稿・コメント | ○ | ○ | ○ | × | × |
| 招待リンク発行 | ○ | ○ | 枠内 | × | × |
| 申請の承認・却下 | ○ | ○ | × | × | × |
| 投稿の非表示 | ○ | ○ | 自分の投稿のみ削除 | × | × |
| 会員の停止 | ○ | ○ | × | × | × |
| 管理者の任命 | ○ | × | × | × | × |
| 監査ログ・データ出力 | ○ | 閲覧のみ | × | × | × |

**公開範囲のルール**

- 投稿の公開範囲は「全会員」「グループ内」「友達のみ」の 3 種。既定は「全会員」
- 画像 URL も認証必須とし、署名付き URL（有効期限 10 分程度）で配信する
- 検索エンジンのクロールは全面禁止（noindex、robots.txt、OGP にも本文を出さない）
- 管理者も「友達のみ」投稿は通報された場合に限り閲覧できる（閲覧は監査ログに残す）

## 6. 非機能要件

クローズド SNS の価値は「中身が漏れないこと」なので、セキュリティとプライバシーを性能より優先する。

| 区分 | 要件 |
| --- | --- |
| 認証 | メール＋パスワード（または Magic Link）、2 段階認証は管理者以上で必須 |
| 認可 | 全 API でロールと公開範囲をサーバー側で判定。DB 行レベルでも制御（RLS 等） |
| 通信・保存 | TLS 1.2 以上、保存データとバックアップは暗号化 |
| 画像 | アップロード時に EXIF（位置情報）を除去、署名付き URL で配信 |
| 監査ログ | 承認・却下・停止・非表示・権限変更・データ出力を 1 年保持、改ざん不可 |
| 不正対策 | ログイン試行のレート制限、招待リンクの総当たり防止、新規会員の投稿頻度制限 |
| 個人情報 | 個人情報保護法に沿ったプライバシーポリシー、本人からの開示・削除請求に対応 |
| 性能 | フィード表示 2 秒以内（95 パーセンタイル）、同時接続 100 人で劣化しない |
| 可用性 | 稼働率 99.5%／月、バックアップ日次・30 日保持、復旧目標 24 時間以内 |
| 対応環境 | 最新版の Chrome・Safari・Edge、iOS / Android のモバイルブラウザ |
| アクセシビリティ | 主要画面で WCAG 2.1 AA 相当（コントラスト、キーボード操作、代替テキスト） |

## 7. モデレーションと運用

入口を絞っても、中でのトラブルはゼロにならない。通報から処分までの流れと SLA を先に決めておく。

**通報対応の流れ**

1. 会員が投稿・コメント・会員を通報（理由を選択式＋自由記述）
2. 同一対象に 3 件以上の通報が集まると自動で一時非表示にする
3. 管理者が 48 時間以内に確認し、「問題なし／非表示／警告／停止」を判断
4. 通報者と対象者に結果を通知し、判断理由を監査ログに残す

**運用ルール**

- 入会申請は 72 時間以内に審査する（超過したら管理者に再通知）
- 管理者は最低 2 人置き、1 人に権限が集中しないようにする
- 利用規約・ガイドライン・プライバシーポリシーは公開前に整備する
- 問題会員が出た場合、その招待者に注意喚起できるよう招待の系譜を参照する

**運営ダッシュボードで見る数字**

- 審査待ち件数と平均審査時間
- 週次アクティブ会員数、投稿数、コメント数
- 通報件数と未処理件数

## 8. 主要データモデル

MVP で必要なテーブルは 10 個前後。招待と監査ログを最初から持つのが通常の SNS との違い。

| エンティティ | 主な項目 | 備考 |
| --- | --- | --- |
| users | id, email, 氏名, ロール, 状態, 2FA 設定, 作成日 | 状態 = 申請中／会員／停止／却下／退会 |
| profiles | user\_id, 写真, 自己紹介, 所属 | users と 1 対 1 |
| invitations | id, 発行者, トークン(ハッシュ), 有効期限, 使用者, 失効日 | 招待の系譜の元データ |
| applications | id, user\_id, 申請内容, 審査者, 結果, 理由, 審査日 | 却下理由もここに残す |
| posts | id, 投稿者, 本文, 公開範囲, group\_id, 非表示フラグ, 作成・更新日 | 削除は論理削除 |
| media | id, post\_id, 保存先キー, 種別, サイズ | 実体はオブジェクトストレージ |
| comments | id, post\_id, 親コメント id, 投稿者, 本文 | 返信は 1 階層まで |
| reactions | post\_id または comment\_id, user\_id, 種別 | 同一ユーザー 1 件 |
| groups / group\_members | id, 名称, 参加方式 ／ group\_id, user\_id, 役割 | Should で追加 |
| reports | id, 通報者, 対象種別, 対象 id, 理由, 状態, 処理者 | 3 件で自動非表示 |
| notifications | id, 宛先, 種別, 参照先, 既読 |  |
| audit\_logs | id, 操作者, 操作, 対象, 理由, 日時 | 追記のみ、更新・削除不可 |

## 9. フェーズ計画と技術スタック案

MVP は Must の 12 機能で、1 人開発なら 6〜8 週間が目安。小さく出して、審査と通報の運用を回しながら広げる。

| フェーズ | 範囲 | 目安期間 | 次に進む条件 |
| --- | --- | --- | --- |
| Phase 0 | 規約・ポリシー整備、画面設計、DB 設計 | 2 週間 | 規約と主要画面が確定 |
| Phase 1（MVP） | Must 機能すべて | 6〜8 週間 | 招待から投稿まで 30 人でクローズドテスト完了 |
| Phase 2 | Should 機能（2FA、友達、グループ、メール通知、ブロック） | 4〜6 週間 | 週次アクティブ率 40% 以上 |
| Phase 3 | Could 機能（メッセージ、イベント、動画、全文検索、アプリ化） | 随時 | 利用状況を見て判断 |

**技術スタック案（1 案）**

| 層 | 候補 | 選定理由 |
| --- | --- | --- |
| フロント | Next.js（App Router）＋ TypeScript | SSR で認証チェックをサーバー側に寄せやすい |
| 認証・DB | Supabase（Auth ＋ PostgreSQL ＋ RLS） | 行レベルセキュリティで公開範囲を DB 側でも強制できる |
| ストレージ | Supabase Storage または S3 | 署名付き URL で画像を非公開配信 |
| ホスティング | Vercel | Next.js との相性、プレビュー環境 |
| メール | Resend 等 | 招待・通知・ダイジェスト配信 |
| 監視 | Sentry ＋ ホスティング標準のログ | エラー検知と監査の補助 |

既存 OSS（Mastodon の承認制登録モード、Discourse の招待制など）をベースにする選択肢もある。自作より早いが、Facebook 風の UI にするにはカスタマイズ量が増える。

## 10. 未決事項

次の 6 点が決まると、スコープと見積もりが確定する。

- [ ] 誰のためのコミュニティか（社内・同窓会・会員制サロン・顧客コミュニティなど）
- [ ] コミュニティは 1 つか、複数を立てられるプラットフォームにするか
- [ ] 入会は「招待＋承認」の二段構えでよいか、承認のみ・招待のみでよいか
- [ ] つながり方は「友達（相互承認）」「フォロー」「全員が全員を見る」のどれか
- [ ] 実名必須か、ハンドルネーム可か
- [ ] 有料会員（月額課金）を将来入れる可能性はあるか

## 11. 実装状況（MVP 公開済み）

Must 12 機能と退会を実装し、Vercel の本番環境（https://kakomi.vercel.app）に公開した。2026-09-27 に、2 段階認証（F-04）とリリースに必要な運用機能を本番に反映した。続けて Phase 2 の Should 機能（F-12 メンションとハッシュタグ、F-15 グループ、F-19 メール通知と週 1 回のまとめ、F-21 ブロック・ミュート）を実装したが、これらはまだ本番に反映していない。判断の記録はリポジトリの docs/adr/0003-phase2.md にある。

| 項目 | 内容 |
| --- | --- |
| 構成 | Next.js 16・React 19・TypeScript、Drizzle ORM |
| DB | Neon（PostgreSQL・シンガポール）。ローカルは組み込み PostgreSQL（PGlite）で DB サーバー不要 |
| 画像 | Vercel Blob（private）。直接 URL では 403、アプリ経由でログインと公開範囲を確認してから配信 |
| 検証 | 単体・結合テスト 173 件（PGlite と実 PostgreSQL の両方）、ブラウザ E2E 10 件、独立エージェントによるセキュリティレビュー（MVP の指摘 12 件、2 段階認証の指摘 5 件、リリース機能の指摘 4 件、Phase 2 の指摘（ブロック 6 件・メンション 2 件・メール 2 件・グループ 4 件）をすべて修正済み） |
| ソース | GitHub の bright-broom/HeyHey（デモ期間中は公開リポジトリ） |

**要件からの変更**

- F-14 友達（Should）の最小版を MVP に前倒しした。F-10 公開範囲（Must）の「友達のみ」が友達関係に依存しているため。
- 招待枠「月 3 件」は「直近 30 日で 3 件」と解釈した。月初リセットでまとめ発行される抜け道をなくすため。
- 登録と申請フォームを 1 画面に統合した。メールのリンクは開くだけでは確認されず、ボタン押下で確認する（メールのリンク検査ボットによる誤確認対策）。
- 認可は DB の行レベルセキュリティ（RLS）ではなく、サービス層の 1 か所（公開範囲の判定）に集約してテストで担保している（docs/adr/0001-architecture.md）。招待・審査・停止の状態遷移と合わせて検証しやすいため。監査ログの追記のみは DB のトリガーで強制している。
- 登録済みのメールアドレスで登録しようとしても画面上は通常と同じ応答にし、本人にだけ通知メールを送る（アドレスの存在確認をさせない）。

**Phase 2 を本番に出す前の手直し（2026-09-27）**

- メンションの入力欄に `@[名前](u:ID)` の記法が見えていたのを、`@名前` だけが見えるように直した（投稿・コメント・編集の画面）。
- 週次アクティブ率の推移を記録するようにした。毎日の定期処理が人数だけを 1 日 1 行残し、管理画面のダッシュボードに週ごとの率と「目標 40% を何週続けて達成しているか」を出す。最終アクセス日時は上書きされるため、記録しないと過去の週の数字が残らず、Phase 3 に進む判断ができない。
